## Captain decision required before implementation

**A — Authorize the additive exact-assistant API or retain the route gap.** Recommendation: approve the single V1 resource with GET baseline and POST conditional action described in the review contract, restricted to the exact latest admitted user and its own empty incomplete assistant, with unknown execution/effect custody refused. Proposed path: `/session/:sessionID/message/:assistantMessageID/continue`. POST carries only `{ userMessageID, expectedRevision }`; 202 means committed/owned acceptance, while typed conflicts distinguish busy, refusal and unconfirmed custody. Sol and Abbe remain ineligible prerequisites. No ordinary prompt/command retry policy, active-peer behavior, live recovery authority or historical tool replay is changed.

This decision adds public request/result/error schemas and generated V1 SDK/client methods. Its direct consumer is Firstmate's exact-session reviewer journal lifecycle owner. Existing Session/message/queue consumers remain compatible; generated consumers gain an additive capability. Unsupported old servers must remain a reported gap, not prompt/restart fallback. This package recommends an additive V1 contract rather than a new global API version. Captain may select a different route/capability boundary or defer it; the runtime author will then adjust the package before implementation. Approval must name the accepted public contract; a healthy live server or an accepted preparation notification is not such approval.
