## Source finding and executed controls

The supplied [Firstmate prerequisite request](/home/byates/fm-firstmate/data/peer-mail/quote-resume-prerequisite-preparation-2026-10-12.md) identifies a real missing supported operation, but its pending-queue-empty early-return explanation does not match this pinned producer. `SessionPrompt.loop` calls `drain`; the early return is guarded by `SessionQueue.empty`, which queries **MessageTable**. A retained projected user makes that predicate false even when `SessionQueue.list` returns no pending items. A truly empty history takes that return and `lastAssistant` throws `Impossible`; it is not the GLM witness. This distinction is executed evidence, not a proposed change to the guard.

The actual problems with exposing raw `loop` are that it joins an existing owner without validating a joiner's root, validates an idle foreign root after starting ownership, accepts a stale same-session root, creates another assistant instead of reusing the retained empty child, selects failed-root retry for an explicit ID, and can proceed to unrelated later input. These broader semantics are useful to existing callers and should remain intact. Add a separately guarded operation at the same owners.

## Minimal proposed public contract

Recommend one additive V1 resource with read and action methods, provisionally `/session/:sessionID/message/:assistantMessageID/continue`. This URL is **not present or callable** in the current API. The path identifies the retained assistant; the original user ID is checked through its parent relationship. A read is preparation, not permission to act. This is a new additive HTTP contract requiring owner review before implementation. Affected readers are Firstmate's exact-session reviewer journal integration and generated V1 SDK/client consumers; existing prompt, command, queue and message GET contracts remain unchanged.

- `GET` returns an exact producer-prepared baseline: session ID, original user ID, assistant ID, an opaque `revision`, recorded serving-writer identity, and `eligible` or a concrete ineligible reason. Compute the revision from a coherent producer snapshot of the exact original user/parts, selected admission order, retained assistant/parts, placement/profile inputs and competing queue custody. Do not expose the full transcript or secrets. Do not use assistant creation time, wall-clock age, or status GET as the revision. No claim, admission, runner adoption or tool dispatch occurs in this read.
- `POST` accepts only `{ userMessageID, expectedRevision }` against that exact assistant path. It accepts no prompt text, command, model override, assistant replacement or review-round change. Validate again at the execution owner. No consumer-computed timestamp or preflight verdict substitutes for the atomic check.
- `accepted` returns HTTP 202 with the exact session/user/assistant IDs, the pre-action revision and serving-writer identity **after** the guarded claim is durably committed and locally owned. It is a scheduling disposition, not a provider-call, token, tool, completion or review receipt.
- `busy` returns a typed conflict without joining, scheduling or starting candidate work. `refused` returns a typed stale/foreign/terminal/nonempty/queued/already-claimed disposition. `unconfirmed` describes insufficient execution or tool custody and starts no work. Foreign/missing linkage follows the existing not-found handling; new typed reasons must be represented in the public schema.

After acceptance, use existing exact-message projections and Session events to observe **the same retained assistant ID**, compared to the returned pre-action revision. Its ID and creation time predate this operation. New durable text/reasoning/tool progress or an attributable terminal result is evidence; acceptance, a claim row, fresh health, unchanged message reads and service exit are not progress. Terminal error is an attributable failed attempt, not permission for another attempt. A lost POST response is unconfirmed delivery: reobserve the original IDs/revision and do not reissue automatically. An already-claimed refusal must never be silently upgraded to success.

## Eligibility at the execution owner

The only initial shape eligible for this phase is the latest original non-`noReply` admitted user with its exact latest **empty incomplete assistant**. Require consistent persisted admission order and original user/parent/assistant/session linkage. Require no completion, error, terminal finish, structured result, partial output, tool record, subtask/compaction obligation, unresolved reservation, pending input or unconsumed promotion. Reject reverted/archived/retention-blocked or changed placement/profile states. Any exception for step-start-only structural parts must be explicitly specified and tested before inclusion; it is not assumed from the word empty.

Use the same process/Instance's native runner, provider/tool/permission/question/background-job custody, not a remote status map. Require Idle and no shell or queued shell continuation. Validate the serving process/store/workspace identity against the baseline; never adopt a different endpoint/session/environment. Existing `EventWriterProcessTable`, `EventAggregateWriterTable` and `EventWriter.readIdentity` distinguish registered process lifetimes using PID, boot ID and start ticks. They are writer provenance, **not** a session execution lease or remote-provider completion receipt. A foreign or unreadable associated writer/owner is a refusal prerequisite; local idle cannot resolve it. Do not repurpose EventV2 replay `owner_id` as a clustered execution lease. The source has no historical provider/tool outcome primitive that can turn unknown custody into proved absence. If the GLM retained state cannot satisfy this positive owner baseline, return `unconfirmed` and preserve it rather than weaken the rule.

Pending queue GET excludes withdrawn holds and promoted-unconsumed rows. Inspect these classes explicitly at the producer's guarded transaction. Preserve unrelated withdrawn originals without restore or deletion; refuse a hold/reservation that makes the selected root ambiguous. Do not invoke `consume`, `promote`, `restore`, `update` or `drain` as a pre-action shortcut. A normal user retry through admission remains subject to #236 and is not this operation.

## Atomic claim and exact assistant reuse

Add a narrowly named idle-only entry to `SessionRunState`/`Runner`, separate from `ensureRunning`. Its conditional transition must reject Running, Shell and ShellThenRun. The same synchronized owner transition must perform the final eligibility check and establish candidate custody; an earlier `assertNotBusy` alone is insufficient. An incoming busy transition that wins must cause refusal. An incoming prompt/assistant/root revision change that wins must also cause refusal before provider work.

Use the existing session queue admission semaphore for the short admission/ownership boundary and an immediate database transaction for the final root/revision/queue checks and durable claim. Release both before provider/tool IO. Establish and test lock order against normal prompt/shell starts; the new work must not enter `queue.consume` while its caller still holds that semaphore. Gate the candidate fiber until the claim has committed, the runner transition is installed, and the short admission boundary is released. A listener must not observe accepted custody and start a competing attempt before ownership is bound. Failure before commit leaves no claim/run or changed assistant. Failure after commit leaves retained claimed custody and attributable error/uncertainty; it must not authorize retry by deleting the claim.

Recommend a single fork-owned `session_v1_continuation_claim` row keyed by the exact assistant ID, with session/user linkage, baseline revision and writer identity. It records only the guarded selection, not provider success or a generic message receipt framework. The existing assistant owns all progress, tokens, tool results and terminal state. A unique conditional insert gives duplicate requests and a second process using this new operation one winner. Keep the claim after completion, failure, transport loss or unknown crash so unchanged historical state cannot start a second run. Retention/deletion and migration ownership must be declared in Core with the other session artifacts; successful retention may remove it only with its original retained messages. A claim is not proof that a legacy/uncooperative foreign runner is absent; the owner prerequisite above still applies.

The assistant schema has no claim slot today, so do not hide control custody in user text, tool parts, timestamps or cost counters. The additive claim artifact needs generated schema/migration and legacy upgrade/rollback proof. Use an unchanged original assistant creation time and ID, and never rewrite its parent. The additive migration's rollback boundary is an old binary that ignores this new operation/claim: it must not reexecute a claimed incomplete assistant through a substitute action. Do not drop live claims to roll back behavior.

Introduce `SessionPrompt.continueExistingUser` as the HTTP-to-owner entry, not an alias of `loop`. Reuse the current processor/provider preparation pipeline for the original selected user and existing empty assistant, with `retryFailedRoot` disabled. Avoid copying the large pipeline: a named shared execution seam is appropriate because normal execution and this operation both use it. The control proves `SessionProcessor.create`/`process` can persist real output under the original assistant ID. Keep normal model/tool/plugin/permission/system preparation and failure finalization there; the control's empty tools/system set is not the production design.

This operation starts the selected existing turn and stops at its terminal/would-idle boundary; it does not call `drain`, fork its waiting drain, or initiate another queued turn. Normal tool continuations within the selected turn remain owned by the same runner and preserve their effect/results. Genuine arrivals after the successful claim retain the existing steer and safe active-peer continuation policy, original admissions/envelopes/reply custody and ten-peer overflow cap; held human input and automation are not converted into a blanket recovery drain. Preserve these existing boundaries rather than reclassifying peers, interrupting tools or adding a scheduler. If later user/peer participation changes answer attribution, retain the original claim's assistant/user association and use the existing source-owned reply attribution; do not report another root's last assistant as the resumed witness.

## Sol: concrete historical-tool prerequisite, not GLM eligibility

The supplied [Sol retained-custody record](/home/byates/fm-saas/data/quote-363-recover-p4/sol-retained-custody-20261012.md) identifies session `ses_ed1c7db23ffeAfcJQ8Vumj7icF`, recovery user `msg_131abf3dd001nxcFyfZOMRNqmZ`, incomplete assistant `msg_131abf4aa001HJcqpYmijZ60IZ`, and four running reads for blind verdict, exchange, final verdict and report. Preserve pin `2d166090c602ee9c3c9a655538a1904407862f7a`, profile, original round and artifacts. The supplied evidence does not include their individual Part IDs/call IDs/full inputs/results; do not fabricate those identities or probe the live store in this preparation. That exact assistant and its four unresolved tool records are the retained prerequisite record set.

Native dispatch provides no attributable historical continuation here. `SessionProcessor.create` initializes an empty `ctx.toolcalls`; `readToolCall`, `updateToolCall` and `completeToolCall` consult that owned map and cannot adopt a historical call by merely reading its projected part. `SessionTools.resolve` binds dispatch to the current processor's assistant, call ID, permission context and execution hooks. The default AI SDK runtime dispatches current provider tool calls; the opt-in native adapter's `LLMNativeRuntime.stream` dispatches current non-provider-executed `tool-call` events through `ToolRuntime.dispatch` and current fibers. Neither path reconstructs the old call's execution handle/result from a database `running` record. The actual retained service's chosen backend is not established by the supplied snapshot; this source trace covers both paths without changing either model/runtime.

`MessageV2.toModelMessagesEffect` converts pending/running records into `[Tool execution was interrupted]` context. The private four-read control proves those synthetic results coexist with unchanged running records and no owned historical completion helper. This conversion does not prove interruption, reads, successful completion or nonexecution. `processor.cleanup`/failure finalization and issue234 prevention do not settle historical outcomes; do not call them to manufacture terminal tool states.

Sol therefore remains refused. The next concrete prerequisite is attributable custody for each retained `(sessionID, assistantID, partID, callID, input, start)` and any genuine execution/result/error witness: either join an actually retained native execution handle and await its real result, or obtain its already-persisted exact outcome. The current fresh-processor primitives cannot do that. If no handle/result survives, a source-owned historical settlement/reexecution policy is required before continuation; the recommendation for this phase is to retain uncertainty and refuse. A read-only tool name is not a dispatch receipt, and issue234's future prevention is not retrospective authorization.
