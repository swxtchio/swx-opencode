# Plan: selected queued-prompt actions

## Contract

- `Ctrl+f` forces only the selected pending item. The queue authorizes the action against current server state, changes the selected item's delivery to steer, and releases only the review hold that requested the force. A preparation in progress, missing item, unconfirmed hold, or another live holder refuses without changing queue custody. A successful action wakes the existing Session drain; the provider/tool work already in progress keeps its ownership. When the force response is ambiguous, the review view performs a read-only, holder-specific hold check and refreshes the queue; it never keeps claiming delivery is paused without a confirmed lease.
- Consolidating a selected human-composer item considers every pending human-composer item. It succeeds only when every member is ready and their delivery and execution context can be represented by one carrier without changing meaning. It preserves each original input, part metadata, receipt and constituent in admission order. Otherwise it leaves the set intact and reports why. A non-human selection keeps the existing consolidation behavior.
- `Ctrl+e` enhances only the selected pending row, regardless of its human or machine provenance, through the existing prompt-enhancement model and rendered-transcript context. The row is rewritten only if its prepared editable text still matches the exact draft sent for enhancement. Its current edited delivery text stays separate from immutable original constituents, so human and machine reconstruction deliver the accepted edit while retaining original provenance. The row's identity, admission/delivery order, receipt, origins, caller part metadata, synthetic context, and non-text parts stay with it; only editable text values and reference offsets change. Stale, preparing, unavailable, textless, empty, or placeholder-losing attempts leave the queue unchanged and report why.

## Implementation

1. Add the force transition to `packages/opencode/src/session/queue.ts`, keeping reservation invalidation, selected-row update, hold release and wake inside one session-locked queue operation; its database writes use the immediate-transaction boundary. Expose a read-only holder status for response-loss reconciliation, and have the TUI update its hold banner and list from that positive server response.
2. Extend queue consolidation with the selected item identity. Use the queue's human-composer and machine-marker classification; build the carrier from original inputs ordered by admission identity, retain the originals needed by later consolidation and delivery, and settle receipts before retiring source rows.
3. Add a queue-owned compare-and-rewrite operation for a prepared pending item. Compare the expected editable text, invalidate any stale reservation and write through `writable()`; preserve the row and receipt while updating editable text and file/agent reference positions. Mark the current delivery override separately from immutable pending-original witnesses so later human and machine grouping uses the accepted edit without rewriting provenance.
4. Wire `Ctrl+f`, selected-item consolidate and selected-item enhance through the queue review dialog and declared HttpApi. Enhancement calls the existing `/prompt/enhance` operation with the composer-selected model and transcript context, then submits only the expected text and returned text to the queue-owned rewrite. Keep the `Ctrl+x`, then `q` review opener and show refusal reasons.
5. Add queue-service, review-dialog, HttpApi and real TUI-to-provider regressions for selection, hold/preparation, human metadata and receipts, plus rewrite CAS and enhancer request behavior. Demonstrate bounded red/green absence proofs for each changed behavior.
6. Regenerate the affected SDK surfaces, add the fork changeset, and run the focused tests, changed-package typechecks, lint and commit-identity gate before pushing the draft.
